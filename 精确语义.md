# 精确语义

工程目标不是实现一个 `qualified = true`，而是保留每个资格截面的独立条件，使系统不能把上一层的成立自动升级为下一层。

核心链路：

`request → claim / fact → policy evaluation → decision → governance basis → authorization → execution → observation → verification → obligation completion → revalidation / discharge`

## 1. 先禁止语义短路

| 已成立 | 不能自动推出 | 新增条件 |
| --- | --- | --- |
| 数据已收到 | 内容为真 | source、provenance、validation |
| 模型高置信 | authoritative fact | authority、evidence |
| fact 可用 | policy 满足 | policy version、evaluation input |
| policy 满足 | Decision 有效 | accountable principal、scope、authority |
| Decision 有效 | approval 完整 | required roles / conditions |
| approval 完整 | runtime 可执行 | current authorization、resource、operation |
| provider success | effect 已发生 | authoritative readback / reconciliation |
| effect 已发生 | 目标达成 | semantic verification |
| 单个 outcome 成功 | case 完成 | independently derived obligations |
| case 完成 | 长期责任解除 | residual obligations、handoff、discharge |
| 历史上有效 | 当前仍有效 | freshness、revalidation、reauthorization |

如果一个字段跨过表中两个以上边界，应检查是否发生语义压平。

## 2. Source、claim、evidence、fact 分开

外部输入进入系统后，至少区分：

`raw input → representation → claim → validated / authoritative fact`

最小字段：

```text
FactClaim
- key / value
- source
- source_ref
- source_version
- observed_at
- provenance
- authority: claim | derived | authoritative
- epistemic_status: unverified | supported | contested | refuted | unknown | revalidation_required
```

AI 抽取、用户输入、缓存、搜索索引和同步副本默认都不是 authoritative source。

记录存在、时间很新、模型很自信，都不能替代 source authority。

## 3. Identity、role、delegation、authorization 分开

Authentication 只回答“是谁”。

运行时授权至少绑定：

```text
Authorization
- principal
- operation
- resource / subject
- scope
- authority_source
- delegation_ref (optional)
- issued_at
- expires_at / revocation_version
```

role、历史 assignment、组织职位、业务 Decision 都不能自动成为当前资源权限。

权限不会自动跨 operation、resource、scope、context 或时间迁移。

## 4. Policy definition、evaluation、Decision 分开

规则定义与规则在当前事实上的结果是不同对象。

```text
PolicyVersion
- policy_id
- version
- owner
- effective_from / until
- definition_digest

PolicyEvaluation
- policy_version
- input_fact_versions
- result
- reasons / unmet_conditions
- evaluated_at

Decision
- decision_id
- subject
- scope
- purpose
- principal
- authority_basis
- policy_version
- input_versions
- disposition
- created_at
```

Decision 必须绑定当时的输入和规则。旧 ID 仍存在，不表示 Decision 现在仍可用。

## 5. 规则适用、激活、执行授权分开

一套规则可以：

1. 对当前对象**适用**；
2. 在当前 scope **激活**；
3. 允许某个 principal 对某个 resource 执行具体 operation。

三者不能合并。

规则适用不产生资源权限；激活也不产生资源权限。

## 6. Governance basis：把“为什么当时成立”冻结下来

高影响 Decision 或 grant 应保存可重建的治理依据：

```text
GovernanceBasis
- subject / case_id
- authority_epoch
- fact_dependencies + versions / digests
- policy_version + definition_digest
- scope
- required approvals / roles
- role / delegation qualification refs
- other domain qualifications
- unresolved_reviews
- expected_self_induced_changes
- created_at
```

用途只有两个：

- 重建“为什么当时成立”；
- 判断“现在是否仍成立”。

执行预期会改变的字段，不应同时被当作“变化即使治理依据失效”的依赖；真正的前置依赖变化则必须触发 revalidation。

## 7. 状态成立与 transition 成立分开

显式 state machine 的每次重要转换至少检查：

```text
current_state
+ trigger
+ expected_version
+ preconditions
+ current_authorization
+ decision / governance basis binding
+ freshness
+ allowed_side_effects
→ next_state
```

还应保存 transition provenance。

合法终点不能证明路径合法。

并发更新使用 version column、ETag、compare-and-swap、optimistic locking 或等价机制；冲突时重新读取当前状态，不以最后写入者覆盖语义冲突。

## 8. Frame condition：只允许改变声明过的范围

一个 operation 应声明自己拥有的变化范围和允许副作用。

执行后不仅检查目标字段，还检查不应变化的关键字段。

扩大 scope、权限、对象集合或副作用类型，应进入新的 review / authorization，而不是沿用旧 Decision。

## 9. Freshness 是依赖仍有效，不只是时间新

当前资格可能因以下变化失效：

- authoritative source 或 source version；
- policy definition / version；
- role、delegation、authority；
- scope / partition / assignment；
- model / data / code / tool；
- dependency / environment / resource；
- 未解决 review；
- 关键 assumption。

因此 freshness 应基于依赖检查，而不是只看 timestamp。

## 10. Review、revalidation、reopen、reauthorization 分开

- **review obligation**：发生需要重新检查的变化；
- **revalidation**：旧 fact、Decision、basis 或 grant 是否仍适用；
- **reopen**：恢复事实收集、候选生成或治理流程；
- **reauthorization**：重新取得执行或长期权限。

依赖变化通常先产生 review obligation，不应自动篡改历史 Decision，也不应自动生成新 Decision。

## 11. Transport idempotency 与 effect idempotence 分开

相同 idempotency key 可以防止重复处理同一请求，但不证明外部副作用可安全重复。

执行记录至少保存：

```text
ExecutionAttempt
- request_id
- decision_id / authorization_id
- subject / resource
- operation
- idempotency_key
- expected_postcondition
- provider_ref
- started_at / finished_at
- transport_result
```

付款、发信、创建账号、授权等操作在 timeout 后可能已经发生。未知结果默认进入 reconciliation，不直接判 failure，也不默认 retry。

## 12. 本地 transaction 与外部一致性分开

数据库 transaction 只能保证本地原子性，不能让数据库和外部系统共同原子提交。

按业务语义选用 transactional outbox、inbox / deduplication、saga、compensation、durable workflow 或 reconciliation worker。

无论实现方式如何，都必须能表示 partial success 和 unknown effect。

## 13. Observation 是现实读取，不是执行器回声

```text
Observation
- authoritative_source
- subject_identity
- source_version
- observed_at
- availability
- freshness
- presence
- state
```

至少能表达：

`present | absent | unavailable | unknown`

以及：

`fresh | stale | unknown`

source unavailable 不等于对象不存在；未验证不等于失败。

## 14. Verification 检查冻结的 postcondition

```text
Verification
- execution / effect ref
- expected_postcondition
- observation_ref
- disposition: verified | absent | mismatch | unavailable | stale | unknown
- differences
- verifier
- verified_at
```

Verification 应读取适当的权威现实源，并检查 identity、目标状态、scope 和非预期副作用。

执行器自己的 success 输出不能替代独立现实验证。

## 15. Effect provenance 必须连续

如果系统声称“一次操作产生了这个结果”，应能追溯：

`request → facts → evaluation → Decision → authority → execution → observation → verification → outcome`

最终状态正确，不足以证明因果链正确。人工、并发操作或重复执行都可能产生相同终点。

## 16. Obligation 独立于 planner

业务必须完成什么，不应由执行 planner 自己定义，否则 planner 漏一步时会得到自洽的假成功。

```text
Obligation
- obligation_id
- subject
- required_state / operation
- authority_class
- required
- source_policy / decision

CompletionAssessment
- obligation_set_ref
- covered_effects
- verified_outcomes
- missing / mismatched obligations
- residual obligations
- satisfied
```

`verified effect ≠ case complete`

`case complete ≠ responsibility discharged`

长期责任还可能需要 handoff、successor、补偿、持续观察或明确 discharge 条件。

## 17. Record、epistemic status、lifecycle 正交

记录类型、认识状态和生命周期不要压成一个枚举。

记录可以是：Evidence、Observation、Assertion、Derivation、Goal、Constraint、Experiment、Decision、Action、Policy、Outcome、Revision、ChangeObject。

同一记录还可以处于：unverified、supported、contested、refuted、unknown、revalidation_required。

历史记录应保留；当前不可用不等于历史删除。

## 18. Audit log 不改写历史

重要链路采用 append-only 或等价可追溯记录。

撤销 Decision、rollback、compensation、reopen 都新增记录，不删除原记录。

至少能回答：谁在什么输入和规则下做了什么；谁授权；执行了什么；现实后来是什么；如何验证；后来为什么修改。

## 19. 语义入口是 trust boundary

来自模型、外部服务、用户或其他系统的内容进入语义核心时，都必须按来源类型校验。

会扩大资格、解除 blocker 或产生副作用的正向 transition，在 source、authority、freshness、scope 或 provenance 缺失时应 fail closed。

Fail closed 只表示“当前不能继续”，不能伪造相反事实。

## 20. 责任角色不要互相冒充

- parser / extractor：生成 representation / claim；
- reasoner：生成候选和理由；
- policy evaluator：计算规则结果；
- decision maker：作业务 Decision；
- authorization layer：授予当前 operation 权限；
- executor：尝试改变现实；
- observer：读取现实；
- verifier：判断 postcondition；
- reconciliation / recovery：处理未知和失败；
- reviewer：处理 revalidation / reopen / reauthorization。

可以由同一进程实现多个角色，但 contract 和记录必须保持角色区别。

## 21. 兼容有多个版本轴

至少独立考虑：

- 数据 / record schema version；
- state-machine semantics version；
- policy version；
- authorization contract version；
- runtime protocol version；
- model / evaluator version。

“旧 JSON 还能解析”不等于语义兼容。

升级时检查字段含义、默认行为、permission、scope、历史解释和 review requirement 是否被悄悄改变。

## 22. 最小可落地 contract

一个会产生真实副作用的系统，至少需要这些对象或等价语义：

```text
FactClaim
PolicyVersion / PolicyEvaluation
Decision
GovernanceBasis
Authorization
ObligationSet
ExecutionAttempt
Observation
Verification
Outcome / ReconciliationState
CompletionAssessment
ReviewObligation
AuditRecord
```

可以合并存储，不能合并语义。

## 23. 最低 invariant

1. AI 输出默认不是 authoritative fact。
2. Decision 不直接生成底层资源权限。
3. 执行前检查 current authorization 和关键依赖版本。
4. 合法终点不证明 transition 合法。
5. scope 扩大需要新的资格。
6. provider unknown 不自动变 failure，也不默认 safe retry。
7. verified outcome 来自现实 readback，而不是 executor 自证。
8. obligation 独立于 planner。
9. correction / rollback / compensation 不删除历史。
10. source、policy、authority、scope 或关键 dependency 变化后进入 review / revalidation。
11. revalidation 不自动续期，reopen 不自动授权。
12. completion 不自动等于长期 responsibility discharge。

## 24. 最低 conformance tests

至少测试：

- 模型高置信 claim 不能直接进入 authoritative fact；
- stale fact / policy / Decision / authority 被拒绝；
- operation 不能超 authorization scope；
- 非法 transition 即使终点合法也被拒绝；
- expected self-induced change 不误伤自己的 governance basis；
- 真正 dependency 变化触发 revalidation；
- timeout / lost acknowledgment 进入 reconciliation，不直接 retry；
- provider success 但现实 mismatch 时不能确认成功；
- cross-effect / cross-subject outcome 不能替代正确 verification；
- planner 漏 obligation 时 completion 失败；
- rollback 后原 Decision、attempt、observation 仍可追溯；
- completed workflow 在 residual obligation 未解除时不能标记 responsibility discharged。

这些测试比术语本身重要：如果一个理论边界不能改变 contract、transition、失败路径或测试，它不应继续占用工程语义层。
