# Guide

这是一组面向普通读者、工程师和产品设计者的实践文档，讨论一个简单问题：

> 当人和 AI 都会犯错、信息永远不完整、行动会影响真实世界时，怎样让判断、决策和自动化系统保持可检查、可纠正、可停止、可恢复？

这里不建立新的哲学体系，也不要求读者接受一套自创术语。文档尽量使用已经广泛存在的语言：事实与证据、模型与不确定性、政策、决策权、授权、执行、验证、审计、恢复、复核和退出。

## 核心观点

1. **模型不是现实。** 观察、解释、预测和分类都只是对现实的有限表示。
2. **不知道不只有一种。** 有时是某个已知变量的值未知；有时连变量、边界、分类方式或问题定义都可能缺失。
3. **建议不等于决定，决定不等于授权，授权不等于执行成功。** 这些边界在 AI 系统中尤其需要显式保存。
4. **API 成功不等于现实目标完成。** 对重要行动，应从独立的现实观察验证结果。
5. **高影响行动应限制暴露范围。** 先缩小权限、对象、时间和并发，再根据新证据扩大。
6. **失败后先重建事实，再决定是否重试。** 当执行结果不确定时，盲目重试可能制造重复副作用。
7. **规则也需要被复核。** 长期有效的政策、权限、模型和流程不能因为过去有效就永久免审。
8. **保留纠错能力本身是一项工程目标。** 异议、替代方案、停止、接管、恢复和退出都需要真实可用，而不是只写在制度里。

## 阅读方式

如果你在做个人判断，先读 01 和 02。

如果你在做 Agent、工作流、行政自动化、企业 AI 或会产生真实副作用的系统，重点读 02 和 03。

如果你关心组织、制度、社会协作以及高度自动化之后还会剩下什么问题，读 04。

## 工程原则

这个仓库有一个刻意的限制：

> 一个抽象概念如果不能改变问题构造、责任边界、状态设计、失败处理、验证方式或测试，就不应为了“理论完整”继续增加到主文档里。

复杂理论、形成历史和更细的个人知识库可以存在于别处；这里优先保留可理解、可使用、可反驳、可落地的内容。
